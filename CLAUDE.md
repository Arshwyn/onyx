## Keeping docs in sync

Whenever a change affects how this project is built, run, deployed, configured, or understood — new commands, new env vars, a new architectural pattern, new tooling — update this file and `README.md` in the same change, not as a follow-up.

## What this is

Onyx is a client-only React + TypeScript SPA for logging workouts, cardio, body weight, and body measurements. There is no custom backend — Supabase (Postgres + Auth + Realtime) is the entire server side, accessed directly from the browser via `@supabase/supabase-js`. All data access, including per-user isolation, is expected to be enforced by Supabase Row Level Security policies (not visible in this repo) rather than by application code.

## Commands

- `npm run typecheck` — run the TypeScript compiler with no emit

### TypeScript

The app is TypeScript throughout (`.ts`/`.tsx`); `tsconfig.json` covers `src/` and `vite.config.ts` in one program (no project references — the split wasn't earning its complexity for a project this size). `strict` is on but `noImplicitAny` is deliberately off: Supabase queries created via `createClient()` without a generated `Database` type resolve to `any`, and much of the app's data (weights, reps, form inputs) is genuinely `string | number` depending on whether it came from a `<input>` or the database, so forcing full strictness everywhere would mean fighting the types more than using them. Shared domain types (`Exercise`, `Routine`, `WorkoutLog`, `CardioLog`, `BodyWeight`, `Circumference`, `UserSettings`, `SetEntry`, `ExerciseStat`) live in `src/types.ts` — reuse those rather than redeclaring shapes per-component. `SetEntry.weight`/`.reps` are optional because a "skipped" set marker (see `DailyView`'s `handleSkipExercise`) stores just `{ isSkipped: true }` with no weight/reps.

### Testing

Vitest (configured via the `test` block in `vite.config.ts`, so it shares Vite's React plugin and resolves paths identically to the app itself) with React Testing Library for component tests. `src/test/setup.ts` registers `@testing-library/jest-dom`'s matchers and calls RTL's `cleanup()` after each test — this is done explicitly rather than relying on RTL's automatic cleanup, since that auto-registration only fires when it detects a global `afterEach` and this repo doesn't run Vitest in `globals: true` mode. Test files sit next to the code they cover (`Foo.tsx` → `Foo.test.tsx`), not in a separate `__tests__` tree.

`dataManager.ts`'s tests mock `./supabaseClient` and drive a small hand-rolled chainable/thenable query builder (see `makeBuilder` in `dataManager.test.ts`) that mimics the shape of a Supabase `PostgrestFilterBuilder` — every method returns the same builder, and `await`-ing it at any point in the chain resolves to the configured `{ data, error, status }` (`status` matters for write tests: `status: 0` is how `makeBuilder` simulates a fetch-level/offline failure, vs. a real HTTP status for a genuine server-side rejection — see `performWrite`/`isNetworkError` in `dataManager.ts`). Reuse that pattern for new `dataManager.ts` tests rather than mocking the Supabase client differently per test. `dataManager.test.ts` also mocks `./lib/writeQueue` wholesale (`enqueueWrite`/`getQueuedWrites`/`removeQueuedWrite` as plain `vi.fn()`s) so its tests assert *decisions* (queue vs. error-toast, replay-and-remove vs. stop-and-preserve-order) without touching real IndexedDB.

`writeQueue.ts` itself is tested separately, in `src/lib/writeQueue.test.ts`, against a *real* IndexedDB rather than a mock — jsdom (this project's Vitest `environment`) doesn't implement IndexedDB, so that file imports `fake-indexeddb/auto` (a devDependency) to polyfill the global before exercising `enqueueWrite`/`getQueuedWrites`/`removeQueuedWrite` directly. Keep that polyfill import scoped to `writeQueue.test.ts` (not `src/test/setup.ts`) — other test files intentionally mock `./lib/writeQueue` instead of touching IndexedDB at all.

### Required environment

The app needs a Supabase project and reads its credentials at build/run time via Vite env vars:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Copy `.env.example` to a local `.env` (gitignored) and fill these in for `npm run dev`. `.env.example` also lists the optional variables: `PORT` (compose host port, default `3010`), `IMAGE_TAG` (compose image tag, default `latest`), `SUPABASE_PROJECT_REF` and `SUPABASE_ACCESS_TOKEN` (Claude Code MCP tooling only, not read by the app or build), and `TEST_USER_EMAIL`/`TEST_USER_PASSWORD` (manual testing). For Docker, they're passed as build args (see `docker-compose.yml` / `Dockerfile`) since Vite inlines `import.meta.env.*` at build time — they cannot be changed at container runtime without rebuilding the image.

### Docker

`docker compose up` builds a two-stage image (`node:26.13.0-alpine3.24` build → `nginx:1.31.8-alpine3.24` runtime, both pinned to exact versions, with the runtime stage running `apk upgrade` for `brotli-libs`, `curl` and `libcurl` at build time; the image is tagged `onyx:${IMAGE_TAG:-latest}`) and serves the static build on host port `${PORT:-3010}` (container port 8080). The runtime is hardened: nginx runs as the non-root `nginx` user (uid 101) with a read-only rootfs, `/tmp` as tmpfs (pid file and temp paths, set in `nginx-main.conf`), `cap_drop: [ALL]` and `no-new-privileges`; the listener is IPv4 only. `nginx.conf` serves `/healthz` (200, no access log, used by the image `HEALTHCHECK`) and does SPA fallback routing (`try_files ... /index.html`) — any new client-side routes must keep working through that catch-all. `nginx.conf` also sets `Cache-Control: immutable` for Vite's content-hashed `/assets/` files and `Cache-Control: no-cache` for `index.html`/`sw.js`/`manifest.webmanifest`/`workbox-*.js` — the no-cache set must stay in sync with whatever `vite-plugin-pwa` emits at the build root, since a cached stale `sw.js` would prevent the PWA's auto-update from ever seeing a new deploy.

### Progressive Web App

The app is installable (Add to Home Screen / desktop install) via `vite-plugin-pwa`, configured in `vite.config.ts`. `registerType: 'autoUpdate'` means a new deploy activates and reloads clients automatically rather than requiring a manual "update available" prompt. The service worker precaches only the built app shell (JS/CSS/HTML/icons) — there is no `runtimeCaching` for Supabase requests, so the app installs and loads offline but data *reads* still require a network connection; offline reads remain intentionally out of scope for most of the app, aside from the `localStorage`-backed caches described under "Data layer" below (exercises, routines, the Today view's daily override/logs/cardio/weight/measurements/PRs) — needed so the two screens users actually open the app for while offline (Today, Log) have something to show and act on. Offline *writes* are handled at the application layer instead (see `src/lib/writeQueue.ts` below), not via the service worker — Background Sync would need the `injectManifest` PWA strategy (a hand-authored SW source file) instead of the default `generateSW` strategy this app uses, so a flush-on-`online`-event approach in `App.tsx` was the lower-friction fit for the existing setup. iOS Safari doesn't read `manifest.json`, so `index.html` also carries `apple-mobile-web-app-*` meta tags and an `apple-touch-icon` link that must be kept in sync with the manifest if branding changes. App icons live in `public/icons/` (`icon-source.svg` is the editable source; the PNGs are generated from it — see git history for the generation script if regenerating at new sizes).

## Architecture

### Routing: `react-router-dom`

`src/main.tsx` wraps `App` in a `BrowserRouter`. `src/App.tsx` renders a `<Routes>` tree mapping real paths to top-level components: `/` → `DailyView`, `/log` → `WorkoutLogger`, `/history` → `HistoryView`, `/trends` → `TrendsView`, `/settings` → `SettingsView`, `/settings/routines` → `RoutineManager`, and a catch-all (`*`) redirects unknown paths back to `/`. Navigation is `useNavigate()`/`useLocation()` (bottom nav buttons call `navigate(...)`; active-tab styling checks `location.pathname`), which gives real browser history — deep links, and back/forward gestures on the installed PWA — for free. This replaced an earlier `view` state string persisted to `localStorage` (`onyx_view`); the URL itself is now the persisted state, so that key is no longer written. `nginx.conf`'s SPA-fallback `try_files` and Vite's dev server both already serve `index.html` for any path, so no infra change was needed to support real routes.

Each `<Route>`'s `element` wraps its component in its own `<Suspense fallback={<ViewLoader />}>` (one boundary per route, not a single shared one) since only one route is ever mounted at a time. `HistoryView`, `TrendsView`, `WorkoutLogger`, and `RoutineManager` are loaded via `React.lazy`, so their code only downloads when the user actually navigates to that route rather than on first paint. `DailyView` and `SettingsView` stay eager (default landing view, and small/frequently reached from the nav bar respectively). When adding a new top-level route, default to lazy-loading it the same way unless it's needed immediately like `DailyView`.

`SettingsView` only ever calls its `onNavigate` prop to reach `RoutineManager` (there's no other cross-view jump), so `App.tsx` wires that prop directly to `() => navigate('/settings/routines')` rather than a generic path-mapping function — don't reintroduce that generality unless `SettingsView` actually grows a second destination.

The `refreshKey` state (bumped on session resume — see below) is passed as `<DailyView key={refreshKey} />` to force a fresh mount after a background/foreground cycle; don't drop that `key` when touching the `/` route.

### Data layer: `src/dataManager.ts`

All Supabase reads/writes are funneled through this single file — components never import `supabase` directly for data (only `supabaseClient.ts` and `dataManager.ts` do, plus auth calls in `App.tsx`/`AuthPage.tsx`). Each exported read function wraps one Supabase table (`workout_logs`, `cardio_logs`, `body_weights`, `circumferences`, `routines`, `custom_exercises`, `global_exercises`, `user_settings`, `daily_overrides`; the latter is read via `getDailyOverride`/`getDailyOverrideState`) and follows a consistent shape: fetch, `console.error` on failure, return `data || []`. When adding new read access, follow this pattern rather than calling `supabase.from(...)` from inside components.

Every mutation (insert/update/delete/upsert) is instead registered once in the `writeHandlers` map near the top of the file — a plain object of `type -> (args) => <the Supabase call>` — and each exported write function (`addLog`, `saveRoutine`, `setDailyOverride`, `setDailyRest`, etc.) is a thin wrapper that resolves whatever it needs (e.g. `getUser()`) and calls `performWrite(type, args, errorMessage)`. `performWrite` is what gives writes offline resilience: if the call fails because the client can't reach the server (see "Offline write queue" below), it persists `{type, args}` to IndexedDB instead of discarding it; if it fails for a genuine server-side reason, it falls back to the old `console.error` + `emitError(...)` behavior. `writeHandlers` is also the replay table `flushWriteQueue()` uses — one definition of "how to make this write," used both live and on replay, rather than duplicating the Supabase call. When adding a new mutation, add its handler to `writeHandlers` and route the exported function through `performWrite` rather than calling `supabase.from(...)` directly — that's what makes it resilient to being offline for free.

`DailyView.tsx` only needs the *viewed date's* body weight/measurements (to show today's entry), not the whole table, so it uses `getBodyWeightByDate`/`getCircumferencesByDate` rather than `getBodyWeights`/`getCircumferences`. Those full-table variants still exist and are the correct choice for views that genuinely need all-time history (`TrendsView.tsx`'s charts) — don't swap those for a date-scoped query without also solving the "all-time" requirement server-side.

`DailyView.tsx`'s personal-record and last-session stats (the "LAST" tag and input auto-population) are computed by `getExerciseStats(exerciseIds, beforeDate)`, which calls the `get_exercise_stats` Postgres function via `supabase.rpc(...)` rather than fetching the full `workout_logs` table. That function — like the RLS policies mentioned above — lives only in the Supabase project, not in this repo; it's `SECURITY INVOKER` (the default), so it runs under the caller's role and the existing RLS policy on `workout_logs` still applies. `getExerciseStats` is called scoped to just the exercise IDs in the currently-viewed routine (not the whole exercise library), since that's all `DailyView` ever renders stats for.

Exercises are a merge of two tables: `global_exercises` (shared defaults) and `custom_exercises` (per-user, prefixed/string IDs); `getExercises()` combines and sorts them. `deleteCustomExercise` guards against deleting anything with an `ex_`-prefixed id (a global/seed exercise id shape), so don't remove that check when touching exercise deletion.

### Offline read caches (`readCache`/`writeCache` in `dataManager.ts`)

Several reads cache their result to `localStorage` on every successful fetch and fall back to that cache if the fetch fails — a deliberate, narrow exception to "offline reads are out of scope" (see the PWA section above), scoped to the two screens users actually open the app for while offline (Today/`DailyView`, Log/`WorkoutLogger`). None of these caches are scoped per-user (same simplification as the `onyx_unit_*`/`onyx_show_*` settings cache already in `localStorage`) — this is a single-user-per-device app.

- **`getExercises()`** (`onyx_exercises_cache`) — without it the exercise picker (`WorkoutLogger`, `DailyView`, `RoutineManager`) would be empty offline and there'd be nothing to log a workout against at all.
- **`getRoutines()`** (`onyx_routines_cache`) and **`getDailyOverride(date)`** / **`getDailyOverrideState(date)`** (`onyx_daily_override_cache_<date>`) — needed to know which routine applies to a given date, and whether it is a rest day. `getDailyOverride` is a thin wrapper over `getDailyOverrideState`, which wraps its cached value in `{ value, isRest }` (entries cached before rest markers existed have no `isRest` and read as `false`) rather than caching the raw result directly, since `null` is itself a meaningful successful result ("no override for this date") that a bare cache read couldn't tell apart from "nothing cached yet".
- **`getExerciseStats(exerciseIds, beforeDate)`** (`onyx_exercise_stats_cache_<sorted-ids>`) — the PR/last-session data. The cache key deliberately omits `beforeDate` (normally "today", so it changes daily) — keying on just the exercise id set means a fetch from any prior day still serves as a same-routine fallback while offline, at the cost of the numbers being very slightly stale in the rare case something relevant happened between the cached `beforeDate` and today.
- **`getDailyViewBundle(dateStr)`** (`onyx_daily_view_cache_<date>`) — wraps `getBodyWeightByDate`/`getCardioLogsByDate`/`getLogsByDate`/`getCircumferencesByDate` (see below) with `Promise.allSettled` and a combined per-date fallback, since those four still need to *throw* on failure for their other callers (see `DailyView.tsx`'s post-write handlers, next section) — caching inside those functions themselves the way `getExercises`/`getRoutines` do would break that. `getDailyViewBundle` is purely an *additional* caller of them, not a replacement; `DailyView.loadDailyView` uses the bundle for its initial per-date load, while the post-write handlers still call the four functions directly and rely on the real throw.

All of these tolerate staleness between syncs — acceptable since having *something* to look at/act on while offline matters more than perfect currency, especially for read-mostly, rarely-changing data (exercises, routines) or data only ever consulted as a fallback when a live fetch already failed.

### Settings: Supabase is the source of truth, localStorage is the cache

User preferences (units, timer increments, show/hide toggles for timer/confetti/body-weight/measurements) live in the `user_settings` Supabase table but are mirrored into `localStorage` under `onyx_*` keys (`onyx_unit_weight`, `onyx_unit_measure`, `onyx_unit_distance`, `onyx_timer_incs`, `onyx_show_timer`, `onyx_show_confetti`, `onyx_show_bw`, `onyx_show_meas`) by `syncSettings()` in `App.tsx`. Components read units/toggles from `localStorage`, not from Supabase directly, so they don't need to be async to render. When `syncSettings()` writes new values, it dispatches a synthetic `storage` event (`window.dispatchEvent(new Event('storage'))`) so same-tab listeners pick up the change — the native `storage` event only fires cross-tab, so this dispatch is required for components in the same tab to notice.

If you add a new user-configurable setting, it needs updates in three places: the `user_settings` schema/defaults in `syncSettings()`'s fallback insert, the mirrored `localStorage` key, and `SettingsView.tsx`'s UI.

`syncSettings()`'s fallback insert is only meant to fire for a genuinely new user who has never saved settings — `getUserSettings()` (`dataManager.ts`) signals that specific case by returning `null` only for a real "no row" result (Postgrest's `PGRST116`), and throws for any other fetch failure so `syncSettings()`'s `try/catch` can tell "insert defaults" apart from "couldn't check right now." It also resolves the user id via the same `getUser()`-with-`getSession()`-fallback helper used elsewhere in the file, not a bare `supabase.auth.getUser()` — that call's network revalidation resolves `user: null` while offline even with a valid local session, which previously made every offline mount/resume misread "couldn't verify user over the network" as "this user has no settings yet" and fire a real (queued, then falsely "synced") default-settings write. On that throw path, `getUserSettings()` also checks `isNetworkError(status)` (the same fetch-level-failure signal `performWrite` uses) before calling `emitError` — a genuine offline/network failure throws silently since it's expected and recoverable, while a real server-side rejection (RLS, malformed query) still surfaces a toast. Keep all of that in place if you touch `getUserSettings()`.

### Surfacing failures: `src/lib/toastBus.ts`

Most `dataManager.ts` *read* functions swallow their Supabase error (`console.error` + return a fallback) and also call `emitError()` from `toastBus.ts` in that same branch, which dispatches a custom `onyx-toast` window event — following the same pattern as the pre-existing `onyx-sync-complete` event in `DailyView.tsx`, rather than introducing a context/state library. `Toast.tsx`, mounted once in `App.tsx`, listens for that event and renders auto-dismissing banners. The legacy `*ByDate`/`getRecent*` read functions instead `throw` on error and deliberately do **not** call `emitError()` themselves, since some of their callers already catch and surface the failure (e.g. `DailyView.loadDailyView`'s catch block) — emitting at the throw site too would stack two toasts per failure there. This means **every call site of a throwing function is responsible for its own try/catch + `emitError(...)`**, and it's easy to add a new call site without one (this bit a `getCircumferencesByDate` refetch in `DailyView`'s save/delete-measurement handlers, which had no catch and silently dropped the failure). When adding a new read function: if it swallows the error and returns a fallback, call `emitError(...)` in that branch; if it throws, every caller must catch it and call `emitError(...)` itself — don't assume some other catch block upstream already covers it.

`getBodyWeights`/`getCircumferences` also throw, joining the legacy group above — they used to swallow like most reads, but `TrendsView.tsx`'s post-write refetch (`handleSaveWeight`/`handleDeleteWeight`/`handleSaveMeasurement`/`handleDeleteMeasurement`) needs to tell "genuinely empty" apart from "the fetch failed and fell back to `[]`" to avoid wiping `bodyData`/`measurementData` on a failed refetch after a write that itself succeeded (queued offline, or synced live) — a swallowing function can't signal that distinction to its caller. Each of those four handlers catches the throw and picks a response based on `navigator.onLine`: offline, apply an optimistic local update (add/remove), reconciled later via `'onyx-sync-complete'`; genuinely online, `emitError(...)` and leave existing data alone rather than fabricate an entry for a write whose outcome is unknown. `DailyView.tsx`'s equivalent handlers (`getCircumferencesByDate`/`getCardioLogsByDate`, already throwing) follow the identical catch-then-branch-on-`navigator.onLine` shape — one consistent pattern across both files, not two.

Writes go through `performWrite()` (see above) instead of calling `emitError()` directly: a genuine server-side failure still calls `console.error` + `emitError(...)` same as a read, but a failure caused by being offline calls `emitInfo('Saved offline — will sync automatically when back online.')` instead, since that's an expected, recoverable state rather than an error. `App.tsx` also tracks `navigator.onLine`/`online`/`offline` events to show a persistent "you're offline" banner — separate from the toast system, since it reflects ongoing state rather than a one-off event. `emitError()` itself checks `navigator.onLine` and no-ops while offline, since the banner already communicates that root cause — without this, going offline fired a stacked error toast per failed *read* on top of the banner (writes no longer hit this path while offline at all, since `performWrite` intercepts them before they'd call `emitError`).

### Offline write queue: `src/lib/writeQueue.ts`

Writes made while offline aren't discarded: `performWrite()` (in `dataManager.ts`) detects a fetch-level failure — postgrest-js resolves those with `status: 0` rather than throwing, which is what distinguishes "couldn't reach the server" from a genuine Postgrest/Postgres rejection (validation, RLS, conflict) — and persists `{ type, args }` to an IndexedDB store (`onyx-write-queue`) via `writeQueue.ts` instead of dropping the write. `flushWriteQueue()` (exported from `dataManager.ts`) replays queued entries through the same `writeHandlers` map in the order they were queued, stopping at the first entry that still fails for a network reason (so order is preserved and nothing is skipped) — a queued entry that fails for a genuine server-side reason on replay is dropped and reported via `emitError`, not retried forever. `App.tsx` calls `flushWriteQueue()` on the `online` event and once on mount if already online (covers reopening the app after connectivity came back while it was closed). Because `writeHandlers` resolves `user_id` once at enqueue time (not at replay time — see `getUser()`'s fallback to `auth.getSession()` below), a queued write still carries a valid `user_id` even if it was made while `auth.getUser()`'s own network revalidation was failing. This only covers writes — offline *reads* remain intentionally out of scope for most of the app (see the PWA section above, and "Offline read caches" under "Data layer" for the deliberate exceptions), so a view that depends on fresh data (e.g. a refetch after a queued write, outside of Today/Log) won't reflect it until the app is back online and reloads. Rest-marker writes (`setDailyRest`) and routine-override writes go through this same queue and replay via `writeHandlers`, so marking a rest day offline syncs later like any other override.

### Session resume / reconnect logic in `App.tsx`

`App.tsx` has a `visibilitychange`/`focus` handler that treats returning to a backgrounded tab as a potential stale-connection scenario: it clears Supabase realtime channels, force-refreshes the auth session, waits briefly for socket stability, then remounts data views via a `refreshKey`. This exists because mobile browsers suspend/throttle sockets in the background. Be careful modifying this — it's timing-sensitive (uses `Promise.race` timeouts), and removing/shortening the delays can reintroduce stale-session bugs on mobile.

This full recovery only runs if the app was actually backgrounded for at least `RESUME_THRESHOLD_MS` (30 minutes) — the handler tracks a `hiddenSince` timestamp across the paired `visibilitychange`-to-`hidden`/`visible` events and computes the gap before deciding. It used to run unconditionally on every visible/focus event, including a one-second app-switch, which force-remounted `DailyView` (losing in-progress set inputs, expanded cards, scroll position) and flashed the "Resuming..." state every single time. 30 minutes is a deliberate choice, not just "long enough" — normal app-switching within a session (checking a notification, glancing at another app, setting the phone down for a bit) shouldn't reload at all; if you need to change it, it's the one constant at the top of the effect.

### Ad-hoc per-day state via localStorage

Per-date overrides live in the `daily_overrides` Supabase table, one row per `(user_id, date)`, and there are two kinds: a routine override (`is_rest = false`, `routine_id` set) changes *which routine runs*, while a rest marker (`is_rest = true`, `routine_id` null) marks the date as a *rest day*. A check constraint keeps them exclusive, so setting one replaces the other, and `removeDailyOverride` deletes the row to fall back to the scheduled routine. Marking a rest day therefore replaces any routine override on that date, and un-resting returns to the scheduled routine; the earlier override is not restored (it is not persisted anywhere). `getDailyOverrideState` also returns `readFailed` (true whenever the online read errored, even if the value came from the cache); the legacy-flag migration skips a date and the swap flow aborts when it is set, so an unknown state never overwrites a real override. `DailyView.tsx` reads both through `getDailyOverrideState(date)` and writes rest markers with `setDailyRest(date)`. The old per-date `localStorage` keys are legacy: `onyx_rest_<date>` is migrated into the table once per device on `DailyView` mount and then removed, and `onyx_swap_<date>` is only ever cleaned up. Do not write either again. The schema change is in `supabase/migrations/`.

### Units

Weight (`lbs`/`kg`), body measurements (`in`/`cm`), and distance (`mi`/`km`) units are each tracked independently and read from their own `localStorage` key in nearly every view (`DailyView`, `HistoryView`, `TrendsView`, `WorkoutLogger`, `SettingsView`). There's no shared unit-conversion utility — each component that displays a unit-aware value does so locally, so when adding a new unit-aware field, follow the existing per-component `localStorage.getItem('onyx_unit_...')` pattern rather than introducing a new global.

### Styling

Tailwind CSS (dark theme, `bg-black`/`text-white` base in `App.tsx`) with no custom design tokens in `tailwind.config.js` — utility classes are used directly and consistently across components rather than extracted into shared style constants.

## Claude Code tooling

`.mcp.json` configures a read-only Supabase MCP server, scoped to a project via `--project-ref=${SUPABASE_PROJECT_REF}` (taken from the environment, no project ref is committed) and locked down with `--read-only`. It lets Claude Code inspect the live schema, RLS policies, and row data directly — useful since the RLS policies enforcing per-user isolation aren't otherwise visible in this repo. The server needs `SUPABASE_PROJECT_REF` and `SUPABASE_ACCESS_TOKEN` in Claude Code's environment (not read from the Vite `.env`); set them in a gitignored `.claude/settings.local.json`'s `env` block (or your shell env) rather than committing it anywhere — `.mcp.json` only ever references `${SUPABASE_PROJECT_REF}` and `${SUPABASE_ACCESS_TOKEN}`, never literal values. This tooling is optional.

### Always verify user-visible changes with Playwright before calling a change done

`npm run typecheck`/`npm run test`/`npm run lint` catch type errors, logic regressions in mocked unit tests, and style issues — none of them prove a change actually behaves correctly for a user in a real browser (a mocked Supabase client and a real one diverge exactly in the offline/network-timing edge cases this app cares most about). For any change to runtime/UI behavior — not just visual tweaks, but anything touching auth, the offline write queue, toasts, sync, routing, or session resume — drive it end-to-end in a real Playwright-controlled Chromium against `npm run dev` before reporting the change as complete, the same way the fix in PR #26 (spurious offline-sync toasts) was verified. Skip this only for changes with no runtime surface to exercise (pure doc/comment edits, test-only changes).

There's no Playwright devDependency or test suite in this repo (this is ad hoc verification, not a project test suite to check in) — Playwright's package and a cached Chromium are already available in the environment: check `~/.cache/ms-playwright` and `npx --no-install playwright --version`. If neither is present, `npx playwright install chromium` will fetch them. Practical notes learned verifying the PR #26 fix:

- Optional, for contributors with their own Supabase project: if you keep a test account's credentials in the gitignored `.env` as `TEST_USER_EMAIL`/`TEST_USER_PASSWORD` (see `.env.example`), use them to log in for real rather than mocking auth.
- To simulate "offline" realistically for this PWA, don't use Playwright's `context.setOffline(true)` — it blocks *all* requests including the localhost dev server itself, which doesn't match reality (the app shell is precached and still loads offline; see the PWA section above). Instead: `page.route()`-abort only requests to the Supabase host (from `VITE_SUPABASE_URL`), and override `navigator.onLine` directly (e.g. via `page.addInitScript`, since some checks read it synchronously at mount) rather than relying on Playwright's network conditions to flip it.
- Prefer writing the throwaway driver script to the scratchpad rather than committing anything Playwright-related to the repo, unless the user asks for a permanent e2e suite.
- When a bug's symptom is specifically about what appears on screen (a toast, a banner, stale data), also run the same script against the pre-fix commit (e.g. a `git worktree add` pointed at `main` on a different dev-server port) as a control — confirming the script actually reproduces the bug pre-fix is what proves the post-fix "no toast" result isn't a false negative from the script itself missing it.
- Clean up afterward: kill any background `npm run dev` processes you started and `git worktree remove` any control worktree — don't leave them running or lying around after verification.
